# PLANET-CONSTRUCTION-LIVE-001 — attempt1

Назначенная база: `5a67a51`, ветка `feature/planet-construction-runtime`. Контракт до реализации, 13 октября 2026. Автор не утверждает готовность к интеграции или ручному тесту до независимого ревью.

Причина: текущие команды всегда отказывают, хотя source startup graph и ordinary definitions уже приняты. Решение: отдельный неизменяемый runtime с серверным адаптером существующих команд; экономика принимает единый candidate с балансами и установленным графом. Старые лабораторные конструкторы остаются явными.

## Граница и hooks

- Новый `M3/Construction` импортирует bounded building/district catalog существующим безопасным importer, оценивает eligibility и source cost/time. Каталог расширения не dependency.
- Start получает `M3StartupColony`, принятый economy catalog и явные resolved numerical modifiers. Создаёт building slots из source zone capacity и district slots из source global capacity. Неизвестные локальные/type/shared ограничения закрывают только соответствующий definition.
- Command adapter принимает существующий `M3ClientCommand`, actor/role/asset/phase guards выполняет до private lookup. Сервер рассчитывает цену, время и refund; strict shape остаётся существующим session validator.
- Economy bridge: неизменяемый bank snapshot с явными `SourceCapped`/`UnlimitedReserve`; переход возвращает runtime candidate и balances. Economy owner под lock строит свой candidate из `Installed`, пересчитывает capacities/upkeep из настоящих definitions и публикует оба только при успехе. Mutable callbacks отсутствуют.
- Day hook возвращает candidate completion **до** единственного monthly settlement; последующий день не заканчивается заранее. Base queue capacity 1. Пока sharing видов не установлен, одновременно допускается один вид очереди; другой вид явно отклоняется `queue-kind-sharing-unresolved`, без выдуманной смешанной FIFO.
- Projection возвращает настоящие `Catalog/Installed/Queue/Slots/Features`; общие `M3GameSession/DevelopmentProtocol/Projection` окончательно соединяет economy owner последовательно после review.

## Поведение и ошибки

Цена фиксируется при заказе, оплата/резерв/очередь атомарны. Повторный commandId с тем же payload возвращает receipt; конфликт, stale, foreign/observer, forged slot, недостаток средств оставляют snapshot прежним. Refund исходному payer ограничен настоящим cap, Unlimited не получает фиктивного cap. Capacity drop сохраняет progress. Подтверждённое пользователем правило **прототипа**: каждый активный день добавляет `1 + текущий speed bonus` единиц базовой работы, положительный factor обязателен; при `completedWork >= baseRequiredWork` заказ завершается в этот день, превышение отбрасывается и не переходит следующему заказу. Price/required base work фиксируются при заказе, bonus читается live; уже выполненная базовая работа сохраняется при смене bonus. Nominal duration = base/(1+bonus), дата завершения при постоянной скорости — ceil этой дроби в днях. Это принятое project rule, не native proof; native daily quantization исследуется отдельно и не блокирует прототип. Zone replacement и clearance остаются отдельными unsupported lifecycle gates. Условия повторно проверяются перед progression; потеря условия отменяет и возвращает paid. Destruction без refund.

### Economy bridge и последовательные hooks

1. `M3ConstructionContent.ImportAsync(root, acceptedPlanetEconomyCatalog)` импортирует безопасные construction definitions. Original source snapshots сопоставляются по hashes между construction/economy. `Create(startup, resolvedStartupContributions)` требует реальные contributions из economy owner для unresolved исходных экземпляров. Ключи — `startup.Buildings[].InstanceId` и `startup.Districts[].InstanceId`; районное значение **на один level**, применяется к каждому установленному level. Identity/kind проверяются; коллекции копируются.
2. Конкретная baseline dependency: capital soldier capacity — `common/inline_scripts/buildings/on_all_capital_buildings.txt:32`, `mult = modifier:job_soldier_or_warrior_add`. `Create(startup)` без resolved contributions явно отказывает, вместо игнорирования этого multiplier. Это seam к уже реализуемому economy resolver, не запрос нового полного reverse. В собственном fakebank harness baseline contributions **явно синтетические**, не доказательство actual starting capacities/upkeep.
3. `Execute(state, bank, actor, existingCommand, evaluation)` проверяет role/owner/readiness/phase/strict shape/revision/receipt, возвращает immutable state и typed deltas. `M3ConstructionEvaluation` содержит detached current context, explicit scoped economy facts и resolved numerical snapshot; для live reevaluation его передаёт world owner. Optional `from?` привязывается **отдельным** `M3ConstructionContent.FromBinding.ActingCountry(bool)` с policy ID `m3-authenticated-acting-country-v1`. В default route без binding значение остаётся `null`; caller обязан взять факт из собственного authenticated M3 acting-country command context, а не вывести его из ordinary owner или startup authority. `M3ConstructionEvaluation` отвергает несоответствие context.FromNomadic и отдельного binding. Это явная политика scope прототипа; native binding optional `from?` остаётся предметом reference research. Точный bounded вопрос reference owner: в `common/inline_scripts/buildings/nomadic_cost_switcher.txt:3,9` optional `from?` при colony construction связан с acting country команды, owner страны, либо другим script scope, и что происходит без привязанного `from`? Пока native ответ отсутствует, prototype binding допускается только из явного authenticated actor context; никакой implicit `false`. Отсутствие evaluation означает только исходный preset context плюс явно переданный from binding, если он есть. Цена stored order не меняется при live modifier update.
4. `ConstructionLiveTransaction.Stage(result, bank)` проверяет весь multi-resource bank candidate; ошибка возвращает **оба** candidate null. Economy owner под существующим lock fork-ит свой мир, применяет validated typed deltas и полностью заменяет source installed contributions из graph (не добавляет их поверх startup второй раз). После успешной проверки публикует мир+runtime; при settlement/error не публикует ни один.
5. `AdvanceDay` возвращает completion graph раньше месячного settlement. Owner передаёт уникальный dayId, current evaluation и validated capacity, один раз собирает все колонии, обновляет district-group levels/zone scaling по `Installed` и исходным zone links, затем выполняет месячную экономику один раз. No carry/early next-day completion проверены. `SynchronizeRevision` связывает runtime с общей economy+construction colony revision, не откатывает receipts.
6. `Project(state, planetId, evaluation, bank, capacity)` вызывается только после existing POV filtering. Реальные slots/installed/orders/features и startup district/zone/feature metadata возвращаются; source image keys намеренно null до asset-manifest binding владельцем общей проекции. Hidden features не публикуются в runtime Features, но остаются в startup metadata с `IsHidden=true`; видимый blocker сохраняет `clearable=true` как категорию с gate `clearance-lifecycle-unresolved`, без clearance slot/quote. `StartupBuildingBySlot` неизменно связывает каждый исходный occurrence с выбранным каноническим building slot; projected `StartupBuildings[].SlotInstanceId` совпадает с `Installed[].SlotId`, `CompatibleZoneInstanceIds` содержит выбранную exact zone occurrence. Это подавляет дубликат в принятой панели по exact slot+definition, не склеивая одинаковые definition IDs. RefundQuote появляется только с actual bank и содержит capped credit. Queue entries с pause сохраняют `status=pending`, ordered position и `gates=[]`: pause управляет только work eligibility, поэтому существующий command consumer показывает разрешённую отмену при `refundQuote`. Информационный pause пока определяется по позиции и supplied active capacity внутри runtime; отдельное UI поле не объявлено. `Reorder` — доверенный runtime hook, новый wire envelope не придуман. Unsupported zones не создают locks/удаления; любые zone/clearance orders отказывают.

Каноническое заполнение building slots: source capacity каждой фактической zone occurrence, затем source startup building order, первое свободное место в accepted compatible occurrence set. Это явно серверная детерминированная реализация legal placement, не заявление о native приоритете. Нельзя трактовать zone slot как одно building место. Unknown source max/scaling прекращает dependent placement; absent slot не заменяется фиктивным.
