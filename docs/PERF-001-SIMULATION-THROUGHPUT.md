# PERF-001 — automatic simulation throughput proposal

13 October 2026. **Approved by integrator/root chat `01a12d71-f1d2-7e31-b692-caaeebd67ace`; backend implementation dispatched after this contract commit.** Parent requirement: [PERF-001](BACKLOG.md#perf-001-показывать-фактическую-скорость-симуляции). Measure successful authoritative automatic days per real second, not requested speed, client FPS, snapshot arrival rate or inverse last-tick duration. No optimization, scheduling change, original-game timing rule or target-hardware performance claim. The 10-second window, 2-second warm-up/stale age and ring size 512 are accepted engineering measurement choices, not native mechanics.

## Existing seams and ownership

`M3Server.Runtime` owns one monotonic Stopwatch and serializes Tick/Execute with its runtime gate (`src/Stellaris.Server/M3Server.cs`, TickAsync/HandleAsync). Snapshot publication reads `M3GameSession.View` every 200 ms (PublishAsync). `M3SessionView` already carries configured `SpeedDaysPerSecond` and `LastTickMilliseconds` (`src/Stellaris.Session/M3/M3Protocol.cs`). Existing UI diagnostics are the `metrics` field, rendered alongside client FPS in the frame loop of `m3-client.mjs`; line numbers differ across UI revisions. Backend owns diagnostic sampling, immutable wire value and server tests; UI owner later handles connection consumption/presentation/tests, sequentially after backend integration. No simultaneous edits to shared files.

Keep diagnostics in the server runtime, outside gameplay state, receipts, sequence and economic commit. Reuse the Stopwatch; add no clock framework or global/core metric. A small read-only session timing observation (phase, paused, configured speed, elapsed day) may expose existing fields under the existing lock to avoid generating a full participant/private world view at 20 Hz. It introduces no mutable state or policy. Runtime compares day before/after its automatic Tick: record exactly one completion only when the authoritative day actually increased by one. Timestamp it from the runtime Stopwatch **after Tick returns**, never from the supplied pre-calculation `now`. Manual Execute/stepDay never contributes. Failed/no-op automatic ticks contribute no days. Sampling must not turn a successful gameplay commit into failure or change its deadline; no diagnostic callback enters the core transaction. B02 scheduling remains unchanged.

## Proposed window and lifecycle semantics

Use a 10-real-second trailing window, with at least 2 real seconds of running observation after reset before publishing a number. For publication time `p`, reset time `e`, window start `a = max(e, p - 10 seconds)`: count successful automatic completion timestamps in `(a, p]`, then rate is that integer count divided by `p - a` in real seconds. Publish the count and actual denominator duration so an independent observer can verify the ratio. This is an event-completion throughput measurement, not a promise of smooth instantaneous speed; boundary/count fluctuations are expected. Floating-point division is diagnostic only and never feeds simulation.

Allocate a fixed ring of 512 completion timestamps per server session, not per player; evict expired entries at recording/publication. If capacity would be exceeded within the live window, mark the metric unavailable and restart warm-up rather than silently discard still-relevant events or report a biased rate. No caller-controlled precision/window size or unbounded samples. Invalid/nonmonotonic diagnostic timestamps likewise yield unavailable/reset, not simulation exceptions or corrected fake timestamps.

Reset at successful start, pause/resume or speed-command schedule resets; a cached/rejected command is not a new reset. Reset on automatic failure/paused state. Initial/lobby state is unavailable (`not-running`); paused state is unavailable (`paused`), not measured zero. Resume/speed reset is `warming-up` for 2 real seconds, with no carry from the previous epoch. Manual paused steps remain excluded. Server process restart creates a new diagnostic epoch. Disconnect/reconnect and observer POV changes do not reset the server-wide metric; a freshly reconnected client waits for a fresh authoritative diagnostic.

Identify a new successful schedule-reset command from actual accepted mutation: compare the existing command sequence before and after Execute, not command type/accepted ACK alone or a changed speed value. A fresh same-value speed command resets; its cached retry does not. Diagnostic failure/overflow/invalid clock input must leave the already committed gameplay result intact and return unavailable, never masquerade as a failed day. Invalid time is not replaced with a corrected timestamp; recovery begins a new epoch only at a subsequent valid sample. An unavailable diagnostic with no valid observation time may carry a null sample timestamp; that cannot refresh client freshness or supersede a timestamped reading.

During a running stall, publication advances `p` even without new completed days: the value decays and becomes measured zero after the window empties. Zero after warm-up is valid and distinct from unavailable. If the runtime gate/calculation stalls snapshot publication too, no refreshed reading exists: the client must label its old reading stale. Do not fabricate server samples while the server cannot publish.

## Additive transport and display

Propose optional `simulationRate` on existing M3 snapshot state, populated by the runtime on the immutable view copy, not stored by `M3GameSession`. Fields: `status` (`measured`, `warming-up`, `paused`, `not-running`, `unavailable`), nullable `automaticDaysPerRealSecond`, `completedAutomaticDays`, `windowSeconds`, and `sampledAtMilliseconds` (finite nonnegative monotonic server elapsed time; diagnostic ordering only, not synchronized UTC). Non-measured states have no numeric rate. No player, fleet, economy, source paths, tokens or other private data. Configured speed and last-tick duration retain their existing meanings. M2 transport is unchanged; absent diagnostic from an older M3 server means unavailable, not zero.

Build the session view and metric observation under the runtime gate, sampling publication time after view construction, then serialize/send outside it. Older world sequence rejection remains unchanged. `M3Connection.receive` currently ignores same-sequence state (`m3-connection.mjs:63–70`); permit a separately handled diagnostic update for the same accepted world sequence with strictly newer `sampledAtMilliseconds`. Do not invoke `onState`, reset renderer interpolation, replace gameplay state or accept a lower world sequence solely to refresh metrics. New world snapshots keep existing behavior. Reset client diagnostic ordering/age on reconnect/session change; reject invalid metric shapes as unavailable diagnostic without weakening world/protocol validation.

Show configured days/s, measured automatic days/s, measured window/count, last tick duration and client FPS as separate labeled values in the existing diagnostics field. Missing/warming/paused/unavailable must be explicit. Age is client monotonic time since receipt of the latest accepted diagnostic; after 2 real seconds without a new sample or on connection loss, mark stale and do not present the last number as current. This age is transport freshness, not a claim about synchronized server sample age. UI-only formatting may round displayed numbers without changing transmitted count/window or simulation arithmetic.

Validation is bounded to this fixed scalar shape: known status; integer count 0–512; finite window 0–10 seconds; finite nonnegative sample timestamp (null permitted only for unavailable); measured status requires window at least 2 seconds and finite rate matching count/window within diagnostic floating-point tolerance (relative/absolute `1e-9`); other statuses require null rate. Invalid or unknown status means unavailable diagnostic, not fallback zero. Missing diagnostics do not renew freshness or overwrite a strictly newer timestamped sample. Fresh diagnostics do not mark assets ready, acknowledge commands, replace stale-world status or bypass connection readiness. No diagnostic samples/history are retained on the client beyond its latest value and receipt time.

## Deterministic oracle and acceptance

The runtime-local bounded diagnostic accumulator accepts explicit TimeSpan samples from production Stopwatch calls. Tests supply exact logical samples directly; no sleeps, busy waits, fake physical slowdown, new clock framework or duplicated simulation implementation. Verify 1/2/4 completed days per second over aligned windows; warm-up; exact left-open/right-closed boundaries; stall decay/zero; duplicate/no-op/failure/manual exclusion; resets and rejected/cached command behavior; restart/reconnect semantics; finite arithmetic, nonmonotonic samples and ring overflow refusal. Runtime checks verify that completion samples follow automatic Tick return and observation matches actual day delta, and that diagnostics cannot mutate gameplay/sequence/deadlines. Existing session atomicity/clock checks remain unchanged.

Test access uses the existing Server project reference from `Stellaris.M3ServerChecks`, with narrowly scoped friend-assembly access to the internal diagnostic helper/runtime. Extract one automatic Tick, Execute and snapshot-publication operation into internal runtime methods actually called by production loops. Tests call these same operations with explicit entry time and an internal diagnostic-only completion sampler; production uses the existing Stopwatch. The sampler does not supply simulation time or enter the economy transaction. An ordering assertion reads the already advanced session inside that sampler, proving actual runtime wiring samples after Tick returns; pure accumulator arithmetic alone is not claimed to prove this. Sampler exceptions yield a logged diagnostic warning/unavailable without changing the original gameplay result. No general clock provider/framework or public injection API.

Wire/privacy tests cover optional fields and no private metadata; UI owner checks same-sequence diagnostic refresh without world reapplication, lower-sequence/older diagnostic rejection, stale/missing/paused/warm-up rendering and unchanged FPS/speed labels. A later bounded live measurement may compare transmitted count/window against independent authoritative day progress over a known uninterrupted automatic interval on configured 1/2/4 speeds, excluding warm-up/reset/manual steps and accounting for event boundaries. Deterministic tests do not establish target-PC throughput; report actual environment and raw observations separately. Backend owns runtime/helper, additive protocol, minimal read-only timing observation, focused server/session checks and this document/report; M2/UI/connection files are excluded. UI adaptation begins only after reviewed backend integration; stable optional RC `9fc45e5` is untouched.
