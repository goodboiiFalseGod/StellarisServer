# M3 — техническая проверка ассетов и рендера

Статус: план сохранён до реализации, 12 октября 2026; эксперимент проведён, [отчёт](ASSET-PROBE-REPORT.md). Пользователь разрешил зафиксировать план, провести проверку и выбрать renderer по результатам. Это разрешение на отдельный локальный стенд, не на реализацию всей M3. Источники: DECISIONS, doc08, CLIENT-DELIVERY-PLAN.

## Цель и границы

Подтвердить путь от локальных файлов Stellaris 4.5.2 до изображения в браузере: mesh → геометрия, DDS → текстура, gfx/asset → связи и материал. Сравнить Three.js и Babylon.js на одних данных. Галактика и система будут 3D, UI остаётся DOM. Не копировать шейдерный движок Paradox целиком; точное совпадение освещения, всех анимаций и VFX не объявлять доказанным одним статическим кораблём.

Установка только читается. Каждый клиент сам предоставляет локальные файлы; сервер раздаёт лишь стенд и зависимости, не ассеты игры. Исходные/производные ассеты, screenshots и зависимости эксперимента хранятся вне tracked исходников (`artifacts/`), не публикуются. Свои readers, adapters, тесты, инструкции и манифест относительных путей/хешей допускаются в Git. Порт стенда отдельный loopback, не 5080/5088. Нативный helper и отключение защиты браузера не разрешены.

## Шаги и свидетельства

| ID | Проверка | Свидетельство |
|---|---|---|
| A01 | Инвентаризация репрезентативных ship/planet/star/Arkship определений и форматов | Относительные пути, magic/chunks, DDS codecs/dimensions, texture/material references, хеши, список неподдержанного |
| A02 | Локальный доступ | UI выбора папки с read-only разрешением, fallback выбора файлов; отмена/отсутствие/ошибка показываются явно. Отдельно отметить, удалось ли автоматизировать настоящий picker; тестовая подстановка File не выдаётся за разрешение OS |
| A03 | Минимальные readers | Bounded binary parsing, проверка размеров/индексов/NaN, явный отказ неизвестного codec/chunk. Реальная модель и DDS + синтетические повреждённые/неподдержанные fixtures. Никаких молчаливых замен потерянных материалов |
| A04 | Два renderer-adapter | Зафиксированные версии, одинаковые геометрия/камера/размер viewport и распакованные RGBA текстуры, материал со явно описанным подмножеством каналов. Без сети к CDN во время чтения ассетов |
| A05 | Браузер | Видимая реальная модель/текстура, orbit/zoom, picking, resize и освобождение/повторная загрузка. Скриншот и структурированный PASS/FAIL, ошибки JS/WebGL |
| A06 | Нагрузка | Один корабль и 200 экземпляров одной геометрии; warmup, frame p50/p95, draw calls где доступны, аппаратный/backend контекст. Только относительное наблюдение на текущем браузере, не SLA всей игры |
| A07 | Регрессии и выбор | Reader-tests, синтаксис JS, прежние тесты M1/M2 если затронуты общие файлы; ревью. Сводка поддержки/пробелов и обоснованный выбор, не только FPS |

Минимальный визуальный образец — один обычный корабль с реальными diffuse и прочитанными связанными каналами, плюс проверка доступности planet/star и Arkship форматов. Если часть материала не воспроизведена, показать ограничение в UI/отчёте. Успешный выбор renderer не означает завершения production importer. Планета/звезда/Arkship могут остаться следующей графической задачей при подтверждённой трудности, с явной записью, не фиктивным PASS.

## Входы, ошибки и ограничения доступа

Браузер получает File/ArrayBuffer, не произвольный путь и не полномочия читать весь диск. Проверять набор ожидаемых относительных имён, размер и тип; никаких upload оригиналов серверу. При отмене сохранить прежний валидный набор. Ошибка разбора не должна оставлять частично обновлённую сцену; ресурсы прежнего набора освобождаются при успешной замене/сбросе. Повторный выбор, утрата разрешения и неподдерживаемый API имеют понятное сообщение.

Для folder picker проверить secure context и наличие API. LAN HTTP M2 не приравнивать к рабочему File System Access. В эксперименте допускается проверенный fallback выбора отдельных нужных файлов: он не считается полной реализацией выбора установки и не снимает вопрос HTTPS для M3.

## Критерии выбора

Обязательные: WebGL2 без обязательного WebGPU; загрузка локальных ArrayBuffer; собственная indexed geometry/материалы; камера/picking; instancing; контролируемый lifecycle; DOM integration; фиксируемая версия и доступная лицензия. Затем сравниваются сложность адаптера, DDS-поддержка, возможности shader-переноса и измерения одинаковой сцены. Если оба проходят, выбрать меньшую необходимую сложность, перечислив цену недостающих функций. Не переносить оба движка в production.
