# M3 — network client and local module publication

UI sub-contract [UI](M3-CLIENT-INTERACTIONS.md). New `wwwroot/m3.html`, `m3.css`, `m3-client.mjs`, `m3-connection.mjs`; M2 app.js/index.html remain unchanged. M3 startup opens/redirects `/` to `/m3.html`. The server build copies only the profile importer/renderer modules and the installed Three build/OrbitControls to separate webroot paths; it does not include Babylon/tests/the original game installation. Three 0.186.1 must already be installed through the existing package-lock; if absent, build fails explicitly with an npm ci instruction, with no silent download at server runtime.

The connection owner has one WebSocket, heartbeat10s, timeout30s, generation guards, and exponential reconnect1/2/4/8s only with a valid token. Commands are disabled until welcome and a fresh snapshot. On reconnect, previous pending commands are replayed with the same commandId after the snapshot; queue≤100, send≤8/s; assetReady is recreated and acknowledged before gameplay replay. An old assetReady ACK does not make the new connection ready. Token/name/role/joinCode/sessionId and bounded pending data may be stored in the tab's sessionStorage as in M2; decoded assets/handles/original bytes are not stored there. Clearing login removes token/pending and stops reconnect. A server restart/different sessionId requires explicit new login/import; it must not automatically occupy a new player-slot.

The manifest is loaded with GET from the same origin; JSON≤1MiB before parsing, with exact template/digest validation. Import starts only after the user selects a folder/files. There is one M3Importer in the UI; abort/pagehide stops the worker. Staged CPU+old CPU+converted GPU-budget≤512MiB are checked before replacement; renderer setProfile must succeed before CPU/icons are published and assetReady is sent. An error preserves the previous set; a new session invalidates its ready state and does not claim that re-verification occurred. For the current reconnect, CPU/GPU are reused, and new assetReady follows welcome/snapshot.

New UI IDs/DOM handlers are isolated from M2. Command buttons and gestures use the same readiness/freshness/role/phase checks. The page explicitly shows localhost origin, profile/import mode, and static approximations. Use safe DOM textContent, never innerHTML with server strings. View factories here are not Unity; DOM ownership/subscriptions remain explicit. There is a single RAF renderer; pagehide releases worker/renderer/connection/timers, persisted pageshow requires explicit reconnection, and the CPU set can be restored from the same page's memory. Connection failure does not destroy the current scene; it only marks it stale.

Automated connection-owner tests: stale callbacks/timeout without close/snapshot pause/ACK replay/new assetReady/foreign session/queue+rate/page lifecycle. DOM tests exercise the actual client module or available pure helpers, not a copy of the logic. Browser QA separately checks module-worker+Three URLs/local File import, UI/lobby/map/order/month/reconnect, 100 switches/stress200. The real Chrome manual gate remains with the user.
