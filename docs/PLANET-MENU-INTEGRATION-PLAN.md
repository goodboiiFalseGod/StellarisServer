# План полной интеграции меню планеты

15 октября 2026. Постановка агенту интеграции. Цель — перенести одобренное меню в рабочий браузерный билд, сохранив его композицию и визуальные состояния, подключить локальные ассеты Stellaris 4.5.2 без модов и реальные данные, команды и механику. Поставкой считается весь функциональный объём ниже; оболочка с работающими отдельными кнопками — промежуточный этап.

Последнее прямое требование пользователя: «Визуальная часть должна остаться по большей части как в нашем результате, только с подключением ассетов из игры». Основой реализации служат HTML и CSS одобренного образца. Подгонка старого интерфейса до приблизительного сходства не выполняет это требование. Разрешены необходимые привязки данных, выделение компонентов, доступность, исправления переполнения и небольшие отступы. Изменение структуры, состава действий или принятого сценария требует обсуждения с пользователем.

## 2. Сохранение визуального результата

Перенести дерево элементов и стили образца в production-компоненты. Удалить демонстрационные обработчики и данные, присоединить адаптер авторитетной модели и существующий транспорт команд. Допустимо переименовать классы или разбить код на модули, если визуальная проверка подтверждает сохранение результата. Старый renderer можно использовать как источник вычисленной модели, но не как новую основу компоновки.

| Блок образца | Что должно сохраниться |
| --- | --- |
| `.pm-window`, `.pm-title`, `.pm-head`, `.pm-stats` | Компактное тёмно-зелёное окно, тонкие рамки, исходная иерархия текста, шапка, панорама, губернатор, сводка и постоянная полоса показателей. |
| `.pm-workspace`, `.pm-main`, `.pm-side`, `.pm-tabs` | Основное содержимое слева, правая внутренняя колонка со сводкой/действиями/очередью; пять вкладок в нижней полосе окна, под содержимым и внутренней правой колонкой. Очередь левее внешнего каталога. |
| `.pm-city-grid`, `.pm-base-slots`, `.pm-city-zones` | Городская карточка; базовые шесть зданий в два ряда по три; две зоны справа друг под другом; у каждой своя тройка слотов. |
| `.pm-rural-row`, `.pm-rural`, `.pm-resource-zone` | Карточки ресурсных районов и их собственные зоны; типовые цвета/полоски, компактная плотность. Данные определяют доступные типы, а не фиксированный демо-массив. |
| `.pm-catalog`, `.pm-choice`, `.pm-building`, `.pm-district-panel` | Отдельная правая панель, карточка с изображением слева и названием/эффектами/ценой справа; те же позиции действий и сведений. |
| `.pm-slot-*`, `.pm-meter`, `.pm-order`, `.pm-confirm` | Согласованные значки, деление 50/50, полоски и сегменты, точное различие установленного и заказанного, компактное подтверждение последствий. |

Цвета, рамки, межблочные расстояния, размеры слотов и пропорции брать из CSS образца. При масштабе 100% его правая внутренняя колонка имеет ориентир 170 CSS px, внешняя — 230 CSS px; сохранить эти пропорции, корректируя только доказанное переполнение. Не заменять плотные карточки крупными плитками, таблицами, отдельными экранами или постоянными текстовыми инструкциями. Ресайз меняет площадь окна, не масштаб шрифта, изображений и кнопок.

**Письменно согласованный минимум 720×480 CSS px при масштабе UI 100% имеет приоритет над уменьшенными CSS/JS ограничениями демонстрационного контейнера.** Его `.pm-stage`, нарисованная карта, тестовые кнопки объектов, встроенные OpenAI widget hooks и mobile media-перестановки не относятся к игровому интерфейсу. Production использует реальную карту и принятые правила окна, не копирует демонстрационную смену колонок при 500 px.

При каждом этапе делать сравнение того же состояния при одинаковых viewport, UI scale и размере окна. Проверять отдельно геометрию с условными изображениями и окончательный вид с игровыми ассетами: другая картинка не оправдывает другую раскладку. Одобренный исходный HTML хранить неизменным; исправления production не записывать поверх эталона.

## 3. Окно и взаимодействие с картой

| Событие | Требуемая реакция |
| --- | --- |
| Открытие колонии с карты, outliner или уведомления | Одно modeless окно объекта. Карта остаётся доступной для перемещения, масштабирования и выбора. Внешний клик не закрывает окно. |
| Перемещение/ресайз | Перетаскивание за шапку, доступный угол ресайза, минимум 720×480 при 100%. Прокрутка внутри содержательных областей; шапка, показатели и навигация вкладок остаются доступны. |
| Другая колония | Обновить то же окно, сохранить общую геометрию и активную вкладку. Закрыть каталог и старые target-specific панели/подтверждения; не выполнять старые обработчики на новой планете. |
| Окно флота, станции или другого объекта | Заменить основное окно колонии, сохранив его геометрию/вкладку для следующего открытия. Простое движение карты не заменяет его. |
| Кнопка закрытия в шапке | Закрыть окно и связанные панели/подтверждения. Сохранить геометрию/вкладку; данные чужой колонии не сохранять как локальную копию игры. |
| Открытие каталога, сведений здания или зоны | Единственный вспомогательный контейнер вплотную справа от всего окна, одинаковой фиксированной ширины. Снаружи совпадает с верхом и низом окна. Закреплённая шапка, прокручивается только содержимое. |
| Справа не хватает места | Сдвинуть окно влево настолько, насколько нужно. Если пара не помещается, поместить панель внутрь справа под общей шапкой, поверх содержимого. Основное содержимое не сжимается. |
| Места снова достаточно | Открытая панель сама возвращается наружу справа, сохраняя target/scroll/focus. |
| Закрытие панели после автосдвига | Окно остаётся в сдвинутом положении; это новая общая сохранённая геометрия. |
| Смена viewport/масштаба | Ограничить сохранённую геометрию видимой областью; шапка и resize handle остаются доступны. Экран меньше принятого минимума проверить отдельно, не уменьшать текст и не вводить новую компоновку молча. |

Общая геометрия и вкладка едины для всех колоний. Приватные модели, каталоги и подтверждения очищаются при смене сессии/POV. `showModal()` для основного окна не подходит: карта становится inert даже с прозрачным backdrop. Модальность допустима для обязательного подтверждения последствий; кнопки подтверждения не должны перекрываться общими сообщениями HUD.

Текстовые пояснения компактных карточек показывать по hover или keyboard focus. Названия, текущие состояния, цены и действия остаются видимыми. Иконки получают доступные имена; запрет текстовых названий ресурсов относится к видимым строкам ресурсов, а не tooltip/ARIA. Отдельных кнопок `ⓘ` у зон/районов нет.

## 5. Районы и зоны

### Районы

- Кнопка «Улучшить» сразу заказывает следующий уровень **того района**, которому принадлежит. Каталог районов по этой кнопке не открывать.
- Учитывать завершённые и зарезервированные заказы, глобальный лимит, лимит типа и общий пул. `planetSize` без модификаторов не является готовой вместимостью.
- Заказ не скрывает кнопку и не заменяет её progress bar. Можно заказать несколько уровней до исчерпания применимого лимита. На лимите кнопка видима и disabled **без причины, подписи и tooltip причины**.
- Полоска и счётчик различают завершённые и заказанные уровни. Все заказанные сегменты одинаковы; active/waiting различается в очереди. Заказанные уровни не дают эффекты и не усиливают зону.
- Город: шесть базовых building slots, сетка 3×2; отдельно две zone occurrences одна под другой. После завершения каждая зона открывает три собственных building slots. Нельзя объединять все 12 в одну сетку или выдавать слоты незавершённой зоны.
- Числа 6/2/3 фиксируют согласованный обычный городской сценарий; startup/runtime обязан дать соответствующий граф. Условные варианты определяются источником и явным покрытием, а не добавлением фиктивных клиентских слотов при неполных данных.

### Создание и сведения зоны

У каждого добывающего района есть свой слот специализации. До разблокировки показывается точное требование технологии/цивика. После разблокировки доступен выбор и заказ зоны. Её эффекты относятся только к завершённым районам своего типа и масштабируются по ним. Цена и требуемая работа зафиксированы при принятии заказа; три слота появляются только после завершения.

Вся карточка завершённой зоны открывает сведения. Клики по вложенному зданию, пустому слоту или отдельному действию выполняют собственный сценарий и не всплывают до выбора зоны. В сведениях — текущие эффекты, связанные здания и «Заменить»; отдельной кнопки информации нет.

Новая строящаяся зона показывает общий значок строительства и прогресс, без изображения выбранной зоны. Её имя видно в очереди. Завершение заменяет состояние заказа рабочей зоной и открывает её слоты одним snapshot.

### Замена зоны

1. Клик по зоне → сведения → «Заменить» → каталог допустимых новых зон.
2. При открытии сведений/каталога нет предупреждения о сносе. После выбора конкретной замены сервер вычисляет точный список **несовместимых** установленных зданий в затронутой zone occurrence.
3. Список пуст — обычный заказ без разрушительного подтверждения. Список непуст — подтверждение с названиями удаляемых зданий и явным предупреждением «без возврата ресурсов». Совместимые здания в список не попадают.
4. Preview привязан к текущим instance/slot IDs и ревизиям. Изменение состава или последствий до подтверждения отклоняет старое согласие без оплаты и требует актуального preview. Сервер повторно проверяет совместимость, не доверяет клиентскому списку.
5. Пока заказ ждёт/выполняется, зона показана 50/50 старой и новой картинкой с прогрессом. Подлежащие удалению здания получают предупреждающий значок; старая зона и здания продолжают работать в прежнем enabled/disabled состоянии.
6. Завершение атомарно заменяет зону, сохраняет совместимые здания и удаляет только подтверждённые несовместимые без refund. Непредусмотренное дополнительное удаление при completion не разрешается старым подтверждением; неработоспособный заказ отменяется по общей политике.
7. Заказы зданий блокируют замену только затронутой zone occurrence. Строительство/замена зоны блокирует новые building orders в ней, не на всей планете. Независимые зоны продолжают работать. Отмена замены сохраняет прежнюю зону/здания и снимает предупреждающие значки.

## 6. Здания и их состояния

Клик по пустому доступному building slot открывает совместимый каталог. Клик по установленному/разрушенному зданию открывает сведения справа и выделяет его слот. Панель содержит имя/изображение, состояние, текущие эффекты и содержание, «Включить/Отключить», «Демонтировать», «Заменить», «Ремонтировать» и отдельную карточку улучшения. Неприменимые действия видимы и disabled с понятной причиной; исключение без причины относится только к кнопке района на лимите.

| Состояние | Слот и сведения | Допустимые действия и завершение |
| --- | --- | --- |
| Locked / свободный | Заблокированный слот или доступное добавление; не смешивать с нехваткой ресурсов каталога. | Открывать каталог только для реального разрешённого слота. |
| Заказ нового здания | Изображение целевого здания и индикатор строительства сразу после авторитетного принятия заказа. | До completion нет effects/jobs/upkeep установленного здания; slot reserved. Новое здание устанавливается включённым. |
| Установлено и включено | Обычная картинка; реальные effects/jobs/upkeep. | Применимые действия из capabilities. Toggle немедленный, без очереди. |
| Установлено и выключено | Обычная яркость картинки и отдельный значок выключения. | Нет эффектов, профессий и содержания. Можно включить или заказать допустимое улучшение/замену. |
| Улучшение waiting/active | Текущая картинка и значок улучшения; progress/time в очереди. | Работает старый уровень. Toggle доступен; демонтаж, замена, повторный upgrade заблокированы до отдельной отмены. Completion наследует enabled **на момент завершения**. Cancel оставляет старое здание. |
| Замена waiting/active | 50/50 старое и новое изображения плюс progress. | Старое работает в текущем enabled-состоянии. Toggle доступен; демонтаж, повторная замена, upgrade заблокированы. Новое при completion **всегда включено**, даже если старое выключили. Cancel сохраняет старое. |
| Разрушено | Разрушенный вид и состояние; отсутствуют effects/jobs/upkeep. | Ремонт по реальному quote и применимые вне ремонта действия по capabilities. |
| Ремонт waiting/active | 50/50 разрушенный/восстановленный вид того же здания плюс progress. | До completion остаётся ruined. Повторный ремонт, demolition, replace, toggle и upgrade заблокированы. Сначала отдельная отмена ремонта. Cancel оставляет ruined; completion восстанавливает работоспособность по контракту instance. |
| Подтверждённое удаление при замене зоны | Отдельный предупреждающий значок; не отключать и не затемнять рабочее здание из-за будущего сноса. | Удаление только при атомарном completion соответствующего заказа зоны. |
| Selected | Рамка/угловые маркеры поверх остальных состояний. | Выделение существует пока открыты сведения; переживает upgrade/replace/repair того же слота. |

«Заменить» закрывает сведения и открывает обычный каталог в том же правом контейнере; дополнительно исключается definition текущего здания. Замена на себя невозможна. Upgrade/replace/repair оплачиваются и выполняются общей очередью. Старое состояние и экономика заменяются атомарно, без двойного начисления эффектов и содержания.

Для улучшения проверять конкретный source→target edge и условия target tech/potential/allow при заказе и пока он pending; потеря условий отменяет заказ. `can_build=no` запрещает строительство с нуля, но само по себе не запрещает допустимый upgrade. Нельзя фильтром обычного строительства случайно удалить разрешённую карточку улучшения.

Демонтаж: отдельное подтверждение с названием здания и отсутствием возврата; после подтверждения немедленное атомарное удаление без заказа в очереди. Связанный заказ не отменяется скрыто; сначала пользователь отдельно отменяет его. После upgrade/replace/repair сведения продолжают показывать новый instance того же slot. Исчезновение самого slot/instance без замены закрывает сведения, сохраняя основное окно.

## 7. Каталоги и ресурсы

Одинаковые правила применяются ко всем строительным каталогам и совместимым вариантам замены:

1. Состав — только открытые игроку, совместимые с точным слотом, разрешённые по условиям и лимитам объекты. Не показывать locked technology, несовместимые, запрещённые уникальностью или другими gameplay-условиями варианты. Требование технологии зоны остаётся на её locked-месте в инфраструктуре, не превращается в запрещённую карточку каталога.
2. Единственная видимая недоступность объекта в каталоге — недостаток ресурсов. Карточка остаётся, но не отправляет заказ. Красным выделяются **отдельно** иконка и число каждого недостающего ресурса; достаточные ресурсы сохраняют обычный цвет. Достаточно обозначить нехватку, отдельный текст с величиной дефицита не нужен.
3. Везде цена, содержание, производство, возврат и потери ресурсов — `иконка + число`, без видимых текстовых названий. Для времени — соответствующий значок и значение. Названия ресурсов допускаются в hover/focus/ARIA.
4. Вся доступная карточка — область заказа. Изображение слева, справа имя, основные эффекты и цена. Один обычный клик оплачивает и добавляет заказ без дополнительного подтверждения, кроме явно разрушительных последствий разделов 5/8.
5. Набор вариантов и affordability обновляются в открытой панели при stocks, технологиях, цивиках, условиях, лимитах, reservations, владельце и слотах. Изменение reserves может не менять colony revision: invalidation должен учитывать все зависимости.
6. Сохранять scroll и focus по стабильному ID. Исчезла карточка — focus следующей видимой; пустой каталог остаётся открытым с «Нет доступных вариантов», focus на закрытие. Не закрывать панель только потому, что новый snapshot содержит пустой список.
7. Если целевой slot перестал существовать или игрок потерял право видеть target, закрыть связанный каталог; это отличается от пустого списка при существующем target. После заказа reserved-slot остаётся отражённым в инфраструктуре; панель продолжает reconciliation, без локального создания новых слотов.

Недоступность транспорта/нет свежего snapshot/не загружен profile блокирует отправку команд отдельно от игровой affordability. Не выдавать это за нехватку ресурса и не показывать технические gate IDs в карточках. Диагностику хранить отдельно от пользовательского сценария.

## 8. Очередь и жизненный цикл

### Отображение и порядок

Очередь находится во внутренней правой колонке. Строка содержит изображение/имя цели, состояние, прогресс, оставшееся время при известном расчёте, отмену и изменение порядка. История completed/cancelled не остаётся активными строками и не сохраняет индикатор строительства в освобождённом слоте.

Обычная колония имеет одну активную позицию и последовательную очередь. Ожидающие заказы можно переставлять между собой, не выше выполняющегося. У номадов/Arkship и Wilderness вместимость `N` задаёт авторитетный source-backed модификатор; первые `N` заказов активны параллельно. Перестановка в первые `N` активирует заказ, вытесненный сохраняет работу в ожидании. Внутри активного блока перестановка разрешена. Изменение `N` сразу меняет states; при `N=0` очередь сохраняется paused без потери работы. Это исключение отличается от неработоспособности отдельного заказа.

Собственного игрового лимита длины очереди нет без подтверждения источником. Инженерные guards `Orders.Count`/`_receipts.Count` на 4096 из исходного runtime не становятся игровым правилом. Для их замены требуется проверенный жизненный цикл receipts/idempotency и bounded transport, а не простое снятие всех ограничений памяти.

### Транзакции и время

- При принятии заказа сервер атомарно проверяет права/условия, фиксирует quote цены и required work, списывает стоимость у payer и резервирует точный slot либо уровень района.
- Клиент не оплачивает и не создаёт установленную сущность локально. Pending отправки отличается от принятого queued order. ACK снимает транспортное ожидание; authoritative snapshot меняет граф, ресурсы и очередь.
- Прогресс начисляется один раз в игровой день. Сохраняется накопленная работа; текущая скорость на начало фазы влияет только на последующие начисления. Human-правило прототипа `daily work = 1 + live speed bonus` не выдавать за доказанную native формулу; source aggregation/rounding остаются отдельными зависимостями.
- Отмена/перестановка/смена `N` меняют active/waiting в той же транзакции, но новый активный заказ получает работу только со следующей штатной дневной фазы. Остаток дня завершённого заказа следующему не переносится.
- Несколько завершений в день применяются в порядке очереди с повторной проверкой каждого. Изменения попадают в соответствующий расчёт экономики месяца. Невалидный следующий заказ отменяется, а не оставляет частичные эффекты.
- Потеря условий отменяет заказ сразу в породившей её транзакции, освобождает reservation и делает refund. Неположительная итоговая скорость или внутренняя ошибка завершения означает отмену, а не бессрочный error/paused. Ошибочная транзакция откатывает частичные изменения.
- Любая передача планеты другому владельцу отменяет **все** её заказы. Новый владелец их не наследует. Refund возвращается исходным payer; исчезнувшему payer деньги не перенаправляются другому.
- Уничтожение колонии отменяет её существование и заказы без refund. Удаление здания при демонтаже/несовместимой замене зоны также не даёт refund или demolition bonus.

### Отмена, подтверждения и уведомления

Ручная отмена доступна для waiting/active/paused и возвращает полную фактически уплаченную стоимость независимо от progress. Refund подчиняется текущим storage caps: принятое количество ограничивается вместимостью, excess теряется.

Если ожидается потеря refund, перед ручной отменой обязательно подтверждение с потерями каждого ресурса `иконка + число`. Preview привязан к ревизиям заказа и запасов; изменение расчёта до подтверждения отклоняет старую команду без отмены и обновляет подтверждение. При нулевой потере отмена сразу, без диалога. После ручной отмены показывать только фактическую потерю, если она была; полный refund без потерь не показывать отдельно.

Автоматическая отмена не требует подтверждения. Уведомление сообщает отменённый заказ и конкретную причину; несколько отмен одной колонии группируются с отдельными причинами. По позднему решению консультации автоматические отмены не выводят перечень excess refund. Исчезновение payer и уничтожение колонии не скрываются: соответствующая причина/одно сводное уведомление. Штатные завершения отдельных уведомлений не создают.

Клик по уведомлению открывает колонию на «Инфраструктуре» и фокусирует сохранившуюся цель. Если колония/target уже удалены или недоступны, не открывать устаревшие данные и не создавать фиктивную цель.

## 9. Контракты UI и сервера

Таблица описывает необходимую семантику, **не объявляет новые поля/команды уже существующими**. Перед каждым server slice закрепить фактическую схему, сериализацию и совместимость. Переиспользовать текущие envelope, IDs, compact tables и validators.

| Модель | Что UI должен получить от сервера |
| --- | --- |
| Контекст окна | Colony ID, owner/видимая перспектива, revision, profile/content fingerprint, variant, доступные разделы/действия, реальные шапочные показатели с различием unknown/0. |
| Районы | Instance/definition ID, completed/reserved levels, global/type/shared capacity, точная разрешённая цель следующего уровня. |
| Граф | Связи district instance → zone occurrence/slot → building slot → installed instance; enabled/ruined, compatible kinds, reservations. Нельзя использовать индекс массива как identity. |
| Каталог | Stable definition ID, локализуемые ключи/изображение, allowed/compatible отдельно от affordability, quote/work, per-resource stocks или affordability, зависимости обновления. |
| Installed actions | По каждому действию target IDs, applicability/reason, revision, upgrade edge, нужный quote/preview. Глобального `canEditPlanet` недостаточно для holdings. |
| Очередь | Order ID, kind, exact target/source/target definitions, payer, порядок, `N`, state, paid/required/completed work, live speed/estimate или unknown, refund preview. |
| Подтверждение | Точный target и вариант, затронутые instance IDs, удаляемые здания/потери ресурсов, ревизии зависимостей, серверный token либо проверяемый fingerprint последствий. |
| Владения | Holding ID/type, owner empire, slot/capacity и публичные эффекты; отдельные per-action capabilities для текущего actor. Чужие частные данные фильтруются до wire. |

Существующие `enqueueConstruction`, `enqueueUpgrade`, `cancelConstruction`, `clearBlocker` использовать только там, где runtime действительно закрывает lifecycle. Новые семантические операции: zone create/replace и preview, building toggle/replace/repair/demolish, reorder, holding actions, actions других вкладок. Имена wire выбрать в контракте; появление кнопки не является реализацией команды.

Каждая команда проходит всю цепочку: UI intent → fresh capability/target → transport pending с `commandId` → strict wire decoder → server authorization/revision/quote/conditions → атомарная mutation → result + актуальный snapshot → reconciliation. Клиент не присылает доверенные цену, refund, эффекты, права или итоговую совместимость.

При повторе того же `commandId` с тем же содержанием не платить повторно. Тот же ID с другим payload отклоняется. `OrderId` идентифицирует заказ, `commandId` — попытку/повтор команды; не смешивать их. Параллельные изменения запасов, слотов и владельца проверяются под серверной транзакцией. Stale/invalid/foreign/insufficient failures не имеют частичных side effects. После stale показывать актуальные данные и повторять разрушительное подтверждение только если оно ещё нужно; молчаливый повтор нового решения запрещён.

UI хранит локально геометрию, вкладку, selection, scroll/focus и незавершённый ввод, но не копию экономики. Inspector привязан к стабильному slot identity: обновление definition при upgrade/replace не закрывает его. Смена POV/сессии/removal обнуляет устаревшие handlers, pending confirmations и приватное представление. Повторное открытие того же таба не оживляет старый callback.

## 10. Владения и права

| Actor относительно владения | Просмотр | Изменение |
| --- | --- | --- |
| Владелец планеты, чужое владение | Владение, его владелец и разрешённые публичные эффекты | Нет. Не отдавать write-права только по владению планетой. |
| Корпорация/оверлорд — владелец конкретного владения | Свои сведения и разрешённые данные планеты | Строительство и изменение своего владения в рамках его условий и лимитов. |
| Владелец другого владения на той же планете | По правилам видимости | Прав на чужой holding/slot нет. |
| Observer/read-only POV | Только разрешённая проекция | Нет, включая прямую подделку команды. |

Если один actor совпадает в нескольких ролях, права на конкретный holding определяются его владельцем/capabilities. Клиентский переключатель demo `role='holdingOwner'` не переносится. UI владельца владения визуально повторяет одобренный результат; планетарный владелец видит тот же раздел в режиме просмотра. Наличие владений не означает их принадлежности владельцу планеты.

Projection, чтение каталога, preview и запись проверяют один и тот же scope. Нельзя просто снять проверку owner в старой команде строительства. Точный payer, принадлежность заказов и membership очередей holdings должны быть source/contract-backed; до этого конкретная операция остаётся зависимостью, а не реализуется догадкой. Полноценный observer read-only требует безопасной проекции: старый M3 мог вообще не отдавать development вне player mode.

| Область UI | Источник и привязка |

| Ресурсы и интерфейсные значки | Иконки соответствующего ресурса/действия; размер и выравнивание из одобренного CSS. Сохранить per-resource красный цвет/маркер нехватки, не обесцвечивая всю карточку. |

| Названия, эффекты, условия и tooltip | Существующая локализация по definition/effect keys; итоговые числа из runtime. Не переносить текстовые demo-эффекты как реальные. |

Переиспользовать `tools/asset-probe/m3-ordinary-planet-assets.mjs`, `m3-planet-assets.mjs`, `m3-profile.mjs`, `m3-planet-images.mjs` и production callbacks `preparePlanetImages`/`appendPlanetImage`/`resolveImageKey` в `m3-client.mjs`; названия и exports сверить на выбранном commit. Расширение профиля включает server manifest/allowlist/hash/version и обе стороны validation, а не только новый `<img>`.

Для каждого класса ассетов фиксировать binding, кадр, правило `contain/cover` и поведение отсутствия. Отсутствующая картинка не меняет размеры блока, не делает доступную игровую операцию фиктивной и не подменяется картинкой другого объекта. Честный fallback допустим в промежуточной сборке; отсутствие обязательных локальных ассетов остаётся пунктом покрытия до полной сдачи.

Иконки 50/50 рисуются как два независимых клиппированных изображения внутри прежней ячейки, поверх — progress/значки. Выключенное здание не затемняется. Удалить буквы/геометрические символы, заменявшие реальные арты; собственные функциональные рамки/индикаторы сохраняются, если уже соответствуют принятому виду.

Установка read-only. Каждый клиент получает ассеты из своего разрешённого локального импорта. Original/derived assets, DLC, screenshots и machine paths не попадают в Git, uploads или public config. Сохранять существующие memory budget/cancellation/disposal: не декодировать заново весь профиль на каждый tick и не утекать handles при смене колоний/панелей. Скриншоты сравнения — только локально в ignored `content-local/references/`; в отчёте ссылки/хеши.

## 14. Что передать следующему агенту

Передача содержит этот план, immutable reference commit/blob, принятый runtime base/result commit, актуальную ownership карту, полный coverage V/C/B/K/Q/T/H/A/R, фактические проверки, известные зависимости и следующую атомарную задачу. Нужные исходные файлы из master переносить точечно; план и договорённости должны быть доступны в рабочей ветке исполнителя, а не только в чужом чате.

Следующий шаг исполнителя: сверить свою незавершённую работу с владельцем, открыть неизменный образец и запустить production на том же размере окна; составить конкретный diff переноса HTML/CSS и привязок к существующей модели. Сначала закрыть визуальное расхождение, затем по этапам довести все команды и вкладки. Сохранять уже корректные transport, economy и asset consumers, не переносить демо-симуляцию. По каждому отсутствующему runtime правилу определить точный источник/владельца, не исключать функцию из плана.

Полная сдача: clean exact commit, независимое ревью без нерешённых замечаний, подтверждённые проверки и browser parity, команда/URL запуска, checklist для пользователя и честный список только оставшихся согласованных исключений. Слияние в master и публикация остаются отдельным действием по разрешению пользователя.
