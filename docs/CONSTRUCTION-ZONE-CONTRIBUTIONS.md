# Source-bound zone district scaling

Source-supported implementation, not C01–C08 approval. `common/zones/99_HOW_TO_ZONE.txt:61–76` distinguishes flat planet modifiers from modifiers multiplied by district level, both plain and triggered. `00_zones.txt:89–91` urban housing and shared city/energy inline job/housing blocks use the triggered district form. Audit found no plain `district_planet_modifier` in the currently selected ordinary/Ark zone files or shared zone inline directory, but it is a documented supported shape and must not silently disappear from imported assessments.

Reuse catalog assessment: add plain `district_planet_modifier` to the same signed housing/job extraction path; absent potential is valid for this plain container. Missing potential on triggered containers remains its separate unresolved engine-default gate. A trusted `ConstructionZoneContributionStager` accepts one assessed **zone**, explicit colony ID/district instance ID/world revision and nullable district level. Bind the result to the exact assessment, which retains numerical/optional condition catalogs. No derived world lineage or default level/count/slot grouping is inferred. Levels 0–4096 are bounded engineering inputs, not a declared native cap; negative/out-of-range/revision/ID inputs fail visibly.

Keep independent ordered raw contributions. For known true, gate-free supported planet modifiers, retain amounts unchanged; multiply supported district-modifier amounts by the explicit level. Preserve signed job/housing values and origins. Missing level gates only relevant district contributions; false branches contribute no amounts and their irrelevant unknowns do not block. Unknown active condition/unsupported modifier/dynamic multiplier gates prevent its staged amounts. The subsequent [triggered multiplier contract](CONSTRUCTION-TRIGGERED-MULTIPLIERS.md) supersedes the original blanket numeric-multiplier gate: source-declared numeric triggered `mult`/`multiplier` scales values exactly, fused with the district factor. Plain modifier multipliers and cost/quote composition remain outside that source rule. Costs, upkeep, work and country/pop-group effects are not part of this planet-capacity/housing staging operation.

Use exact checked decimal × integer multiplication: detect overflow **and loss of representability**, not .NET decimal's possible implicit precision reduction. Construct an exact decimal only when its normalized coefficient fits 96 bits; no rounding. On any numeric failure, return an overflow/precision gate with **no staged contributions**, including earlier ones. Other active unknown gates remain aggregated and visible. This is pure source-bound staging, not applying an incomplete subset to a colony. The later [installed zone contract](CONSTRUCTION-INSTALLED-ZONES.md) recognizes the exact raw flat `zone_building_slots_add` key in zone assessments and stores it separately; amenities and other unsupported effects still gate the batch. No final usable-slot composition, employment, resources, quote, queue, calendar or live endpoint is introduced; neither contract permits economic suppression.

Acceptance: flat versus district signed amounts, ordered separate branches, exact source/instance/level/revision binding, levels null/zero/maximum and malformed inputs; false/unknown relevance; source numeric/dynamic mult not silently applied; plain container assessment; exact decimal precision and overflow rollback after earlier contribution; immutable results. Real zone definitions assess and stage with unsupported effects/defaults visibly gated, not forged complete application. Existing construction/session regressions and independent actual-diff review required.
