# M3 — серверное построение metadata-профиля

Подконтракт [manifest](M3-ASSET-MANIFEST.md), до подключения HTTP v2. Отдельный read-only builder в Stellaris.Core/Assets; не менять ContentSession/M1 и его текущую политику версии. Использует собственный фиксированный список тех же 44 относительных путей, что m3-profile.mjs; обязательный parity-test сверяет наборы. Версии/visualId соответствуют v2-профилю.

Builder принимает только корень установки, не произвольный список путей от клиента. `launcher-settings.json` проверяется как metadata версии: rawVersion строго `v4.5.2` (так записано в реальной установке), в DTO gameVersion=`4.5.2`; размер ≤1 MiB. Никакого prefix matching 4.5.x. Он не игровой asset и не добавляется в browser files[]. Все 44 файла читаются только read-only с ограничением 64 MiB/файл (строже общего потолка 128 MiB, как действующий reader); каталог не сканируется. Путь относительный с `/`, без пустых/`.`/`..` сегментов, colon/control/absolute; символические ссылки/reparse points в корне/цепочке зависимостей отклоняются, чтобы лексическая проверка не читала за пределами установки.

SHA-256/byteLength каждого файла вычисляется потоково с CancellationToken; после первого полного прохода повторно проверяются версия и все 44 зависимости. Изменённый источник, missing/unreadable/oversize/version mismatch — видимый отказ с относительным именем, без абсолютного пути и оригинальных байтов в DTO/ошибке. Нет кеша на диске и нет модификации установки. Успешный builder возвращает immutable manifest и canonical digest v1; исходные массивы/streams не остаются в DTO.

DTO: schemaVersion=1, profileId=m3-static-452-v2, profileDigest (lowercase64hex), gameVersion=4.5.2, importerVersion=1, materialProfileVersion=1, files[] ordinal-sorted `{relativePath,byteLength,sha256,kind}`, visuals[] из четырёх согласованных ID `{visualId,dependencies,materialProfile}`. MaterialProfile=`m3-static-approx-v1`. На этом этапе каждый visual ссылается на весь атомарный 44-файловый профиль; UI тоже часть обязательного набора. Это не дополнительный каталог/произвольный shader. Canonical bytes/digest строго по родительскому контракту; численные значения invariant-culture, LF, без BOM. Сериализация web camelCase и UTF-8 metadata ≤1 MiB проверяется до HTTP-публикации следующим этапом.

Приёмка: точные версии/44 paths/4visuals/kind, canonical UTF-8 независимый golden vector с не-ASCII и ordinal sorting, изменить bytes/hash/длину→другой digest; invalid/path traversal/duplicate/несовместимая версия/лимит/reparse point/cancel; коллекции не изменяемы извне. Реальный read-only запуск на локальной 4.5.2 и parity с JS. Synthetic fixtures не копируют оригинальные файлы игры и создаются только во временной папке; удаление ограничено этой проверенной папкой. HTTP/session integration реализована; результаты отдельно в M3-INTEGRATION-VALIDATION, не в этом контракте.

## Дополнительные детерминированные регрессии

Между завершённым первым production hash-pass и повторной проверкой допускается минимальный internal test seam (без публичного callback/API, только friend test assembly). На synthetic fixture он изменяет один byte с сохранением длины; BuildAsync обязан отказать без возврата частичного manifest, с относительной безопасной ошибкой. Неизменённый fixture должен проходить тот же seam; отмена в этой точке должна прервать операцию и освободить handles. Production путь без seam сохраняет прежние два hash-pass/три version-check. Никаких тайминговых гонок или изменений реальной установки.

На Windows дополнительно проверить directory junction без symlink privilege: link как root, ancestor корня и внутренний каталог обязательного пути; обычный каталог — положительный контроль. До BuildAsync проверить реальные ReparsePoint attributes и разрешённый target. Junction создаётся только в выделенной synthetic temp-папке; удаляется native PowerShell Remove-Item -LiteralPath без -Recurse, после проверки exact link/target и границ fixture. Helper теста использует PowerShell 7 (`pwsh.exe`): Windows PowerShell 5 запрашивает подтверждение для непустой ссылки в этой среде. Это зависимость только теста, не сервера/импортера. Target sentinel должен сохраниться; рекурсивная очистка fixture допустима лишь после удаления всех известных links и проверки отсутствия reparse points, без обхода их targets. Если junction или helper недоступен, сохранить точную диагностику как SKIP, не объявлять guard проверенным; ошибка unlink — FAIL без опасного fallback. Успешная junction-проверка не закрывает отдельный SKIP file/directory symlink.
